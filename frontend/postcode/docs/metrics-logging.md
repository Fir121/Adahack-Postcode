# Metrics diagnostics

The proxy previously returned 502 for every thrown fetch error, including its 12-second deadline, and discarded the cause. It passes upstream 503 responses through; it does not generate 503 itself. A past failure cannot be identified retrospectively if no diagnostic entry was captured.

## Logs and correlation

- Frontend: `frontend/postcode/logs/api-proxy.log`, plus the Next.js server console. `API_LOG_LEVEL=info|warn|error|off` controls verbosity; `API_LOG_FILE` overrides the file path, relative to the frontend process directory. The file rotates at 5 MB with one backup. Failed file writes fall back to console logging.
- Backend: `backend/logs/api.log`, plus stderr on the machine running the API. `BACKEND_LOG_LEVEL=INFO|WARNING|ERROR` and `BACKEND_LOG_FILE` override defaults. The file rotates at 5 MB with two backups. Backend changes require restarting/redeploying the API behind ngrok.

Each proxied request generates an `X-Request-ID`, forwards it to the API, and returns it to the browser. The updated backend includes the same ID in request, database and external-service logs. Copy it from the failed request's response headers in browser Network tools and search both logs:

```sh
rg 'YOUR_REQUEST_ID' frontend/postcode/logs/api-proxy.log backend/logs/api.log
```

Entries include UTC timestamps, route, status, elapsed milliseconds and error classification. Backend exceptions include redacted tracebacks, including failures during startup. Database operations and carbon intensity, postcode lookup and air quality calls have start/completion/failure entries. Request bodies, query values, email IDs and URL credentials are excluded or redacted. A read-only deployment without file access can collect the structured console output instead.

## HTTP failures

| HTTP status | Diagnostic event | Meaning |
| --- | --- | --- |
| 502 | `upstream_connection_error` | Proxy could not connect/read; check `error_code` such as `ECONNRESET` or `ENOTFOUND` |
| 502 | `upstream_non_json` / `upstream_invalid_json` | Upstream successful HTTP response contained HTML or malformed JSON |
| 503 | `upstream_http_error` / `upstream_non_json` | Actual upstream API/tunnel 503; original status and any ngrok error code are recorded |
| 504 | `upstream_timeout` | The proxy's 60-second deadline expired; formerly reported as generic 502 |

Other upstream HTTP errors retain their status. JSON error responses generated by the proxy also contain a stable `code` and `requestId`, without raw upstream HTML or stack traces.

The proxy allows 60 seconds for an upstream response, and the browser allows 65 seconds so it can receive the proxy's timeout response. These values are defined together in `lib/api/config.ts`. Environmental calls still allow 15 seconds individually, and postcode detail performs multiple lookups sequentially; the larger proxy budget accommodates those lookups and database work. The timings expose which stage was slow; these logs do not eliminate network outages. Missing environmental data now returns `null` without crashing valid community scores or rankings. The metrics list also reads user counts once rather than once per postcode.
